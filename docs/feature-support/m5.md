## Bring-up

The first substantive finding from the team's own M5 work, and the one currently
blocking progress.

### Secondary CPUs do not execute

On M5 Pro (`t6050`) the secondary CPUs never run any code under m1n1. CPU 0
comes up; the rest stay silent.

They are not switched off. PMGR reports the cores powered on, so this is not a
power-management failure. The better description is that their memory access is
gated — the cores are up but cannot reach what they would need to fetch.

M5 Max shares the `t6050` SoC ID, so it is expected to behave the same way. That
has not been tested.

The failure is specific to one boot arrangement:

| Boot object | Secondary CPUs |
| --- | --- |
| m1n1 as a bare Mach-O boot object, iBoot handing off directly | Do not execute |
| A custom XNU-like kernelcache | Come up normally |

The kernelcache case rules out a hardware or silicon-revision problem: the same
machine starts its secondary CPUs without trouble when the boot object is a
kernelcache. What differs is how iBoot prepared the machine before handing over.

### iBoot takes two different paths

Disassembly of iBoot shows two entirely separate code paths, one for XNU and one
for a custom OS. That is the shape of the bug: the custom-OS path skips
initialisation the XNU path performs, and whatever the secondary CPUs need is in
the skipped part.

Two things have been tried and did not help:

- Mimicking iBoot's sequence from m1n1. The attempt faults.
- Waiting for a firmware change. macOS 27 beta 6 behaves the same as earlier
  betas.

!!! note "How this sits against the Secure Boot notes"

    [Secure Boot](../research/security/secure-boot.md) records the split as raw
    boot object versus Mach-O, with only the Mach-O object loaded under SPTM.
    The split observed here runs between a bare boot object and a full
    kernelcache, both Mach-O. Which distinction iBoot actually keys on is not
    resolved.

### SPTM is not a way out for Linux

The kernelcache works because it runs under SPTM, and SPTM is built for XNU
alone. Adopting it to get the secondary CPUs is not a trade that is open to us.

XNU allocates pages through an abstraction, so having SPTM own frame management
and page-table updates underneath costs it little. Linux makes assumptions about
page tables throughout the kernel, and there is no single layer to redirect.
Running Linux under SPTM would be a large refactor of the kernel rather than a
port to a platform.

Windows is the more plausible candidate of the two, because it runs in EL1 —
which is where SPTM expects its client to sit. It is still a different project
from this one: there is no m1n1 in that picture at all, and page tables would
have to be managed through SPTM's private API.

Neither is a path to booting Linux on M5 Pro. The initialisation gap in iBoot's
custom-OS path remains the thing to solve.
